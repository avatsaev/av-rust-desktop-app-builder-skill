# Repository files, pinning, contribution rules, licences

In every path below `myapp` stands for the project's machine name.

## Repository files beyond the code

The template generates every file below. A real repository needs all of them, plus two lock files.

| File | Purpose | In the template |
|---|---|---|
| `README.md` | What the app is, how to build and run it | Generated |
| `AGENTS.md` | The rules, the workspace map, and the commands to run before finishing. People and coding agents both read it first | Generated |
| `docs/architecture.md` | The layer table and the seams, kept current | Generated |
| `docs/development.md` | Build, test, run, drive programmatically, environment variables, debugging | Generated |
| `docs/contributing.md` | The "add a command" checklist and style | Generated |
| `docs/control-protocol.md` | Every control method and its params | Generated |
| `LICENSE-MIT`, `LICENSE-APACHE`, `NOTICE` | Licensing | Generated |
| `ATTRIBUTION.md` | One row per bundled asset: path, title, author, source, licence | Generated |
| `SECURITY.md` | How to report a vulnerability. Files, automation input and the webview are untrusted | Generated |
| `.github/dependabot.yml` | Dependency update pull requests for cargo, npm and GitHub Actions | Generated |
| `Cargo.lock` | Committed: an application pins its dependencies | Committed after the first build (`cargo generate-lockfile`) |
| `apps/myapp/package-lock.json` | Committed: the gate installs with `npm ci`, which needs it | Generated |

Keep these current as the project changes: when a layer, a seam, a command-adding step or a control
method changes, update the matching file in the same change.

`.gitignore` keeps the build outputs and secrets out of the repository:


## A starting `AGENTS.md`

````markdown
# AGENTS.md

MyApp is a native desktop app: a headless Rust engine, and a Tauri window whose webview
(React + TypeScript) draws what the engine publishes. Read `docs/architecture.md` next.

If the `av-rust-desktop-*` agent skills are installed, use them: `av-rust-desktop-develop` for
everyday changes, `av-rust-desktop-architecture` for the rules in depth.

## Workspace map

    crates/doc              L1  the model: pure data
    crates/ops              L2  history
    crates/format           L3  native file format
    crates/engine           L5  Session + command registry (every action is a command)
    crates/shell            L6  UI state, generated menus, control protocol (no UI toolkit)
    crates/testkit              test helpers
    apps/myapp                  the web frontend: React + TypeScript, thin
    apps/myapp/src-tauri        the desktop binary: Tauri window, dialogs, control server
    apps/myapp-cli              headless CLI
    xtask/                      cargo xtask layers | web | wasm | test | ci

Layering is enforced by `cargo xtask layers`. Register a new crate in `xtask/src/layers.rs`.

## Golden rules

1. The core is Rust. Web technology lives only in the frontend (`apps/myapp/src`), and the
   frontend is thin: it draws the view it is sent and sends command ids. No business logic, no
   document state and no file or network access in TypeScript.
2. Never crash. Non-test Rust code has no unwrap, expect or panic, and no unsafe. Return errors.
   Input is hostile: check bounds, cap sizes, bound recursion. A crash fix ships with a test that
   panicked before it.
3. Everything is a command. User-visible behaviour is a command in
   `crates/engine/src/*_cmds.rs` with id, label, menu, shortcut, params doc, `enabled`, `run` and
   tests. The frontend, the CLI and the control channel dispatch ids.
4. A crate depends only on lower layers. Nothing below the app binary uses tauri, wry or tao.
5. UI state is data. What automation should see lives in `crates/shell/src/state.rs`; the frontend
   keeps only what a widget needs while it is on screen. Colours come from the tokens in
   `apps/myapp/src/tokens.css`. Look at a rendered image (`npm run snapshot`) before calling a UI
   change done.
6. The webview gets the least it needs. It may call the app's two commands and listen for one
   event; no plug-in permissions, a strict CSP, no remote content in the main window.
7. Never break wasm. File-system code is `cfg(not(target_arch = "wasm32"))` or behind `Services`.
8. Tests are the gate. Every change comes with tests.
9. Permissive licences only, for crates and npm packages alike. Check a dependency's licence
   before adding it; record every bundled asset in `ATTRIBUTION.md`.

## Conventions

- Command ids (`<area>.<verb>`, camelCase) and control methods are public API. Never rename one
  after a release.
- An error says what was wrong and, where possible, what would be right.
- A command that cannot run now returns the reason: it is the menu item's tooltip and the message
  an agent reads.
- A check that looks removable carries a comment saying what it prevents.
- Machine names are lowercase (`myapp`); everything a user reads says `MyApp`.

## Before you finish

    cargo test -p <crates you touched>
    cargo clippy -p <crates> --all-targets -- -D warnings
    (cd apps/myapp && npm run check && npm run lint && npm test)     # when the frontend changed
    cargo xtask ci

Stop and ask before anything hard to undo: publishing, releases, secrets, spending money,
destructive git.
````

## Pinning git dependencies

- Pin an immutable revision (`rev = "<full hash>"`), never a branch.
- Keep every crate from one repository on the same revision unless there is a reason not to, and say
  the reason in a comment.
- CI may reject git dependencies from outside your organisation (see [CI](ci.md)).

## Upgrading Tauri

Keep `tauri`, `tauri-build`, every `tauri-plugin-*` crate and the npm `@tauri-apps/*` packages
(`@tauri-apps/api`, `@tauri-apps/cli`, and any plug-in package you add) in step: the Rust versions
live in `[workspace.dependencies]`, the npm ones in `apps/myapp/package.json`, and `@tauri-apps/api`
follows `tauri`'s minor version. Upgrade them together, then:

1. Run the gate (`cargo xtask ci`).
2. Run the app on each platform you ship: the webview engine differs per platform and the gate runs
   on one.
3. Look at a rendered snapshot (`npm run snapshot` in `apps/myapp`).

## Contribution rules worth adopting

- **Check before you start.** Read the issue and search open pull requests for the same fix.
- **Verify, don't guess.** Open a definition before using it; confirm the cause in the code.
- **Keep fixes narrow and tested.** Fix what the issue describes, where the bug is, with a test that
  fails without the fix.
- **Review your own diff** before opening a pull request: identifiers exist, the test fails without
  the fix, nothing unrelated changed, the description is true.
- **Report only what ran.** Say what you tested and what you could not.
- **`main` changes through pull requests only.**
- **Keep secrets and personal details out** of the repository, logs and requests.
- **Don't change CI in a feature or fix pull request.**

## Permissive licences only

Crates, npm packages and bundled assets use licences from an allowlist: `ISC`, `MIT`,
`BSD-2-Clause`, `BSD-3-Clause`, `Apache-2.0`, `OFL-1.1`, `CC0-1.0`, `CC-BY-4.0` and similar. Check a
dependency's licence before adding it, whether it comes from crates.io or npm. Record every bundled
asset (path, title, author, source, licence) in `ATTRIBUTION.md` in the change that adds it. The
template's own row is the placeholder icon in `apps/myapp/src-tauri/icons/`; replace it before
release.

Study other products for behaviour only. Never copy their code, strings, shaders or assets.
