# A tour of the template

What `new-project.sh` writes, part by part, and what to look for in each. Paths are inside the
generated project; `myapp` stands for the project's machine name and `MyApp` for its product name.

The template is the complete source of a small application: a checklist with undo, a file format,
menus, shortcuts, a Tauri window, a CLI and a control channel. The sample domain is deliberately
trivial. Every structural part of a real application is present, and there is no domain logic in
the way of seeing it. The `av-rust-desktop-design` skill lists what to replace.

## The tree

```text
myapp/
├─ Cargo.toml                 workspace: members, shared dependency versions, lints, profiles
├─ .cargo/config.toml         the `cargo xtask` alias
├─ rustfmt.toml  clippy.toml  .gitignore
├─ .config/nextest.toml       test runner profile for CI
├─ .github/workflows/ci.yml   one job that runs `cargo xtask ci`
├─ .github/dependabot.yml     grouped updates for cargo, npm and GitHub Actions
├─ README.md  AGENTS.md       what the app is; the rules people and agents read first
├─ ATTRIBUTION.md  SECURITY.md  NOTICE  LICENSE-MIT  LICENSE-APACHE
├─ docs/                      architecture, development, contributing, control-protocol
├─ crates/
│  ├─ doc/                    L1  the model
│  ├─ ops/                    L2  history (undo and redo over snapshots)
│  ├─ format/                 L3  native file format (bytes to model and back)
│  ├─ engine/                 L5  Session + command registry
│  ├─ shell/                  L6  UI state, generated menus, shortcuts, control protocol: the view as data
│  └─ testkit/                    test helpers
├─ apps/
│  ├─ myapp/                  the desktop app: an npm project (the web frontend) …
│  │  ├─ src/                 … React + TypeScript, thin
│  │  ├─ scripts/snapshot.mjs render the frontend to a PNG without the app
│  │  └─ src-tauri/           … with the Rust binary `myapp` inside: the Tauri window, dialogs, control server
│  └─ myapp-cli/              headless CLI
└─ xtask/                     layers | web | wasm | test | ci
```

99 files.

## Reading order

To understand the design, read in this order and skip the rest until you need it:

1. `crates/engine/src/session.rs`: `execute` and `edit` carry the whole design.
2. `crates/engine/src/commands.rs`, then `item_cmds.rs` as the pattern for your own commands.
3. `crates/shell/src/lib.rs` and `control.rs`: the shell and the one value the frontend draws.
4. `apps/myapp/src-tauri/src/bridge.rs` and `commands.rs`: the whole boundary to the webview.
5. `apps/myapp/src/App.tsx` and `components/Items.tsx`: how little the frontend does.
6. `xtask/src/layers.rs`: the rules as data.

## Workspace root

Versions, lints and profiles live in the root manifest; member crates say `workspace = true` and
nothing else. Things to understand before changing `Cargo.toml`:

- **`members`** names the desktop crate by its path, `apps/myapp/src-tauri`: it sits inside the npm
  project, the layout every Tauri tool expects.
- **`[workspace.dependencies]`** is the only place a version is written. Internal crates are listed
  too, so a member writes `myapp-doc = { workspace = true }`.
- **The Tauri family moves together**: `tauri`, `tauri-build` and every `tauri-plugin-*` stay on
  the same major version, and `@tauri-apps/api` in `apps/myapp/package.json` follows `tauri`'s
  minor.
- **`[workspace.lints]`** forbids `unsafe` everywhere. Each library crate opts in with
  `[lints] workspace = true`.
- **`[profile.dev.package."*"] opt-level = 2`** optimises dependencies even in debug builds. Your
  own code stays at 1 for fast rebuilds.
- **`[profile.release]`** has no `panic = "abort"`, on purpose: the crash guard needs unwinding.
- **`log`** has its `std` feature on: the app installs its own boxed logger.

Other root files:

| File | What it does |
|---|---|
| `.cargo/config.toml` | The alias that makes `cargo xtask <command>` work: `xtask = "run -p xtask --"` |
| `rustfmt.toml` | `max_width = 160`, `use_small_heuristics = "Max"` |
| `clippy.toml` | Lets tests use `unwrap()`, `expect()`, `panic!` and indexing while production code may not; cognitive complexity threshold 30 |
| `.gitignore` | `target/`, `node_modules/`, `dist/`, `gen/schemas/` (generated by tauri-build), `*.log`, and `*.token`: control-channel tokens are credentials |
| `.config/nextest.toml` | A `ci` profile: no fail-fast, a hang timeout, failures repeated at the end |

## Core crates

The crates below the engine. None of them knows about commands or UI.

### `crates/doc`: the model (L1)

Pure data. This is the crate you rewrite for your domain. Keep its properties:

- Everything derives `Clone`, `PartialEq`, `Serialize` and `Deserialize`.
- A field added later gets `#[serde(default)]`, so older files still load.
- Invariants are checked here, in `validate()`, with an explicit cap on every size
  (`MAX_TEXT_BYTES`, `MAX_ITEMS`): the data may come from a file or an agent.
- Identity is a typed id (`ItemId`), never an index. Indices change under undo.
- New ids are derived from the data rather than from a stored counter, so a file cannot supply a
  counter that collides.

### `crates/ops`: history (L2)

Undo and redo over snapshots. A state is an `Arc<Document>`: recording one costs a pointer, and
there is no per-command inverse operation to write or get wrong. `History` keeps at most 50 undo
steps by default and drops the oldest first.

`History` does not own the current state. The session passes it in and gets the state to show
back, which keeps this crate free of any session logic.

### `crates/format`: the native file format (L3)

Bytes in, model out, and back. There is no file system access here; the engine does the reading
and writing.

The envelope carries a format name (`FORMAT`) and a version (`VERSION`) from the first release.
`decode` reads those two fields first, so a foreign file or one from a newer version is refused
with a message that says so, and an older version has one place to be migrated. `MAX_BYTES`
(16 MiB) is the largest file it accepts.

### `crates/testkit`: test helpers

It depends on no workspace crate, so any crate can use it as a dev-dependency without a cycle. The
layer check rejects it as a normal dependency. It holds `adversarial_params()`, the hostile params
the command fuzz uses.

## The engine: `crates/engine` (L5)

The `Session` that owns the open model, and the command registry. It is the façade every frontend
talks to, and it has no UI toolkit in it.

| File | What to look for |
|---|---|
| `Cargo.toml` | `tempfile` is a normal dependency on native targets only: it is what makes saves atomic, and a wasm32 build has no file system |
| `src/error.rs` | One enum for the crate. `Disabled` carries the reason a command cannot run now; `BadParams` names what was wrong with the input |
| `src/session.rs` | `execute` finds the command, checks the params are an object, checks `enabled`, and runs the command inside `catch_unwind`. `edit` clones the model, lets the closure change the copy, and publishes the copy with one history step only when the closure returns `Ok`. `revision` grows with every change, undo and redo included, and is what `dirty()` and any cache compare against |
| `src/commands.rs` | `CommandSpec`, and `build()`, the one list of command modules. The `enabled` helpers `always` and `has_doc` cover most commands |
| `src/params.rs` | Params come from the frontend, scripts and agents. A missing key is `None`; a key of the wrong type is an error that names the key and says what was found |
| `src/item_cmds.rs` | The sample domain's commands. A command module is a `specs()` list and one function per command. Its tests cover behaviour, undo, disabled states and bad params |
| `src/edit_cmds.rs` | Undo and redo are commands like any other, with `enabled` predicates that say why they are unavailable |
| `src/query_cmds.rs` | `command.list` and `document.inspect`: queries are what agents call first, and `document.inspect` is the document half of what the frontend draws |
| `src/file_cmds.rs` | The wasm split. The same command ids exist on every target; the half that touches the file system is compiled only where there is one. `write_atomic` writes a temp file in the same folder, flushes it and renames it over the target, so a crash or a full disk mid-save leaves the previous file intact |
| `tests/panic_hunt.rs` | The adversarial fuzz. Every registered command is run with params nobody asked for, each call on its own thread with a 10-second deadline. A process-wide panic hook counts panics, because `Session::execute` would otherwise turn a command's panic into an ordinary error and hide it. The test is `#[ignore]`d so that a plain `cargo test` stays fast; the gate always runs it. A command added later is covered with no extra work |

## The shell: `crates/shell` (L6)

Everything a frontend needs that is not the engine, with no UI toolkit in it. It turns the engine's
state into one value to draw, and it is where automation reads and drives the same thing.

| File | What to look for |
|---|---|
| `src/lib.rs` | `AppShell` holds the session, the UI state and the services. `run` tries shell commands first and then the engine, and puts any error in `ui.status`. `answer` handles one `Request` |
| `src/state.rs` | `UiState`: what the shell remembers that is not the model and that automation should see (`theme`, `hide_done`, `status`). What a widget needs only while it is on screen stays in the frontend |
| `src/menus.rs` | The menu bar as data, generated from the registry (`model`). `invoke` is what a menu click or a shortcut does: a command that needs something only the platform can ask for (a file) gets it here through `Services`. `UI_COMMANDS` are the shell commands, which change only view state |
| `src/shortcuts.rs` | Shortcut strings from the registry are parsed here, so a bad one fails a Rust test, and they reach the frontend as data |
| `src/services.rs` | Platform services are optional hooks. This crate has no file dialog, clipboard or OS code of its own; where a hook is missing, what needs it is disabled and says why |
| `src/control.rs` | The control protocol: four methods and no transport. `view` builds the value the frontend draws, which is also what `ui.inspect` returns. `ui.set` validates every field and then applies them all, so a refused request changes nothing. `Request` and `Envelope` are what crosses the channel to the owner thread |
| `src/tests.rs` | Headless shell tests: menus and their disabled reasons, `invoke` with a fake file picker, the control protocol, requests answered from a channel. No window, no webview |
| `examples/view.rs` | Prints the view after a script of control calls. The snapshot tool feeds it to the real frontend |

## The desktop app: `apps/myapp`

All platform code lives here, and all web technology. The layer check exempts the binary, and
nothing may depend on it.

### The Rust binary: `apps/myapp/src-tauri`

| File | What to look for |
|---|---|
| `Cargo.toml` | The crate has its own `[lints]` with `unsafe_code = "deny"` instead of the workspace's `forbid`: it writes no unsafe code, but Tauri's macros generate the app context here and must be able to allow it |
| `tauri.conf.json` | The product name, the application id, the main window, the content security policy and the bundle settings. It sets no version (the one in the workspace manifest is used) and no `devUrl`, so a plain `cargo run -p myapp` uses the built frontend |
| `tauri.dev.conf.json` | What `npm run app` adds: Vite's dev server on port 5173, for hot reload |
| `capabilities/default.json` | What the main window's webview may ask of the app: `core:default` and nothing else. File dialogs are opened from Rust, so the webview gets no plug-in permission |
| `icons/` | A placeholder application icon in every size the bundler wants. Replace it with `npm run tauri icon <your-1024px.png>` |
| `src/main.rs` | Parses arguments, binds the control port before the window opens (so a port in use is a startup error, not a silent no-op), creates the one channel every request takes, and starts Tauri with the dialog plug-in, the bridge and the two commands |
| `src/commands.rs` | The two Tauri commands, and nothing else: `control(method, params)` and `invoke_command(command)`. `#[tauri::command]` generates code that names `unreachable!`, so this module alone allows that lint |
| `src/bridge.rs` | `Bridge` is the webview's way to the owner thread. `spawn_owner` starts the thread that owns the `AppShell`: it opens the file from the command line (under the crash guard), answers requests one at a time, and after each sends the webview a `view` event when the view changed |
| `src/services.rs` | The desktop's implementation of the shell's hooks: file dialogs through `tauri-plugin-dialog`, called on the owner thread, never on the main thread |
| `src/control_server.rs` | The loopback control server. Socket threads only parse and forward on the same channel the webview uses. Its safety properties: loopback only, the first line must authenticate, the token comparison takes the same time wherever two tokens differ, a request line is bounded, and a token file is created readable by its owner only |
| `src/crash_guard.rs` | The last-resort guard. Code returns errors and never panics; this is the net for a panic that escapes anyway |
| `src/logging.rs` | A logger small enough to own. The app's own crates log at `info`, everything else at `warn`. `MYAPP_LOG=debug` or `trace` raises the app's level |

### The web frontend: `apps/myapp` and `apps/myapp/src`

React 19 and TypeScript 7, built by Vite. Thin by design: it draws the view and sends ids.

| File | What to look for |
|---|---|
| `package.json` | The scripts: `dev`, `build`, `check` (`tsc --noEmit`), `lint` (oxlint), `test` (vitest), `tauri`, `app` (the window on the dev server), `bundle` (installers), `snapshot`, `snapshot:install` |
| `.oxlintrc.json` | The lint rules for `npm run lint`: correctness, the React hook rules, no `any`, and the thin-frontend rule as code (no Tauri import outside `src/lib/backend.ts`, no network or storage globals) |
| `vite.config.ts` | Relative URLs (`base: "./"`), the fixed dev port, and the test setup (jsdom, `src/**/*.test.{ts,tsx}`) |
| `index.html` | The page: one `<div id="app">` and the entry script |
| `src/main.tsx` | Renders `App` inside `<StrictMode>` with the backend `connect()` chose |
| `src/lib/types.ts` | The shapes the shell sends (`View`, `UiState`, `DocumentView`, `Menu`, `Shortcut`) and the `Backend` interface. Kept in step with the Rust side by hand |
| `src/lib/backend.ts` | The only file that imports `@tauri-apps/api`: `tauriBackend()` wraps the two commands and the event; `staticBackend(view)` draws a fixed view with no app behind it, which is what the snapshot tool uses |
| `src/lib/shortcuts.ts` | Compares the parsed shortcuts with key events: modifiers must match exactly, `Cmd` is Ctrl off macOS, and a focused text field keeps its own undo and clipboard keys |
| `src/App.tsx` | The whole screen is a function of one value, the view. It listens for the `view` event, asks for `ui.inspect` once, applies the theme, and turns shortcuts into ids. Each effect cleans up after itself: `<StrictMode>` runs effects twice in development |
| `src/components/MenuBar.tsx` | Draws the generated menus: label, shortcut, a disabled item's reason as its tooltip, a toggle's check mark. Which menu is open is its own state |
| `src/components/Items.tsx` | The sample panel. It reads the document and dispatches command ids. The text being typed is its own state and becomes a command's params on Add. A checkbox is a controlled input: the click only asks for the change, and the box shows the document's state |
| `src/components/StatusBar.tsx` | The last command's error, or a summary |
| `src/tokens.css`, `src/app.css` | Design tokens as CSS variables, one block per theme, and the base styles that use them |
| `src/App.module.css`, `src/components/*.module.css` | Each component's own styles, as a CSS Module beside it |
| `src/**/*.test.{ts,tsx}` | Component tests (React Testing Library on jsdom) with a fake backend (`test-support.ts`): what a click dispatches, what a view draws. `tokens.test.ts` fails on a colour literal in any style sheet or component outside `tokens.css` |
| `src/test-setup.ts` | Unmounts what each test rendered and tells React that tests run inside `act`. Vitest runs without global test functions, so React Testing Library cannot register these itself |
| `scripts/snapshot.mjs` | Renders the built frontend to a PNG in a headless browser, with the view taken from the real shell |

### `apps/myapp-cli`: the headless CLI

The proof that the engine needs no window: the same commands, run from a terminal or a script.
Results are JSON lines on standard output and diagnostics go to standard error. `run` parses every
`--cmd` before running any, so a typo in the last one does not leave the first ones applied and
unsaved. Its integration test (`tests/cli.rs`) runs the built binary, which is what a script or an
agent sees.

## Tooling and CI

### `xtask`

A small binary in the workspace, run as `cargo xtask <command>`. It is plain Rust, so the gate
behaves the same on every OS. Add project tasks here (code generation, reports, release helpers)
rather than as shell scripts.

- `xtask/src/layers.rs`: the layer check. The rules are data: `TABLE` assigns each crate a class,
  `UI_CRATES` lists what only the top layer may use (`tauri*`, `wry`, `tao`, `muda`, `webview2*`,
  `webkit2gtk*`, `winit`, `rfd`), and `check` reports violations over a small model built from
  `cargo metadata`. The rule engine has its own tests. A crate missing from `TABLE` is a
  violation, so a new crate cannot skip the check.
- `xtask/src/main.rs`: the dispatcher and the gate. `cmd_ci` is the single definition of "green".
  It prints a summary that names the step that failed and the steps it skipped. `cmd_web` runs
  `npm ci` when `node_modules` is missing, then the frontend's type check, lint, tests and build; it
  comes before clippy because Tauri embeds `apps/myapp/dist` into the binary at compile time.

### `.github/workflows/ci.yml`

A standalone workflow that installs system packages, Rust and Node.js and runs the gate. Actions
are pinned by commit, the token is read-only, and only `main` writes the build cache. The step
before the gate fails when `Cargo.lock` does not match the manifests. The gate cannot check this
itself: `cargo xtask` is a plain `cargo run`, which refreshes a stale lock file before any
`--locked` step sees it.

This workflow has not been run. The pinned action commits were checked to exist in their
repositories on 2026-11-11.

## How the template is stored in this skill

`assets/template/` holds the files above with conventions that `new-project.sh` undoes. Keep them
when you edit the template:

- A path component `dot-x` becomes `.x` (`dot-gitignore`, `dot-github/`, `dot-cargo/`,
  `dot-config/`). Installers and package managers drop or reinterpret real dotfiles.
- A trailing `.tmpl` is removed (`README.md.tmpl`).
- The placeholders `com.example.myapp`, `MyApp`, `MYAPP`, `myapp`, `__YEAR__` and `__AUTHOR__` are
  replaced, in file contents and (for `myapp`) in paths. Image and font files are copied as they
  are.
- `apps/myapp/package-lock.json` is part of the template. After changing `package.json` there,
  regenerate it in a scaffolded copy with `npm install` and copy it back.

Because of these conventions the template does not build in place. Scaffold it to a scratch
directory to build it.
